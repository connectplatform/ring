## Module boundaries (operator view)

| Stage | What happens |
|-------|----------------|
| **Ingest** | Cron polls IMAP for UNSEEN mail, or a signed webhook pushes parsed payloads |
| **Process** | Security scan → AI classification → CRM contact/thread upsert → draft queue |
| **Review** | Admins open `/admin/email-inbox` and `/admin/email-drafts` to approve or edit replies |
| **Send** | Approved drafts go out via SMTP with proper threading headers |
| **Track** | Tasks and API cost roll up in admin analytics |

Idempotency is built in: duplicate `Message-ID` values are skipped, and overlapping poll batches are mutex-guarded.

</Audience>

## Persistence — `jsonb-collection` → `db()`

CRM repositories and services never call raw SQL. They import helpers from `features/email-crm/lib/jsonb-collection.ts`, which delegates to the platform database singleton:

| Helper | `db()` method |
|--------|---------------|
| `readDoc(collection, id)` | `readDoc()` |
| `upsertDoc(collection, id, record)` | `readDoc()` then `updateDoc()` or `createDoc()` |
| `queryDocs({ collection, filters, orderBy, limit })` | `queryDocs()` |
| `deleteDoc(collection, id)` | `deleteDoc()` |

`db()` is exported from `lib/database/DatabaseService.ts` and resolves the active adapter from `DB_BACKEND_MODE`.

## Active JSONB collections

All CRM tables use the **platform JSONB row model** (`id`, `data`, `created_at`, `updated_at`):

| Collection | Document id | Indexed fields |
|------------|-------------|----------------|
| `email_threads` | RFC thread root / Message-ID | `status`, `fromEmail`, `lastMessageAt` |
| `email_contacts` | `contact_<sha256(email)>` | `email`, `type` |
| `email_messages` | RFC Message-ID | `threadId` |
| `email_drafts` | `draft_<uuid>` | `threadId`, `status` |
| `email_tasks` | `task_<uuid>` | `threadId`, `status`, `dueDate` |
| `email_api_usage` | `req_<timestamp>_<random>` | `timestamp`, `operation`, `emailId` |

Migrations: `009_email_crm_jsonb.sql` (threads, contacts, messages, drafts) + `010_email_crm_tasks_jsonb.sql` (tasks, api usage).

Factory: `getEmailContactService()` / `getEmailTaskService()` / `getEmailDraftService()` use Postgres unless `EMAIL_CRM_PERSISTENCE=memory`.

## Idempotency and concurrency

1. **DB dedup** — `EmailMessageService.exists(messageId)` at start of `handleEmail`.
2. **Poll mutex** — overlapping `pollInboundBatch` returns `{ skipped: true }`.
3. **Await handlers** — `pollBatch` waits for all `handleEmail` promises before disconnect (no truncated AI pipeline).
4. **Webhook** — `uid === 0` skips IMAP `markAsSeen`.

## Cron vs IDLE

| Mode | When | Mechanism |
|------|------|-----------|
| **poll** (recommended) | k8s CronJob, serverless | Connect → fetch UNSEEN → process → disconnect |
| **start** | Dedicated Node pod | Persistent IMAP IDLE via `instrumentation.ts` |
| **HTTP start** | Debug only | `EMAIL_PROCESSOR_ALLOW_HTTP_START=true` + cron `action:start` |

## Security

- Cron/webhook: fail-closed `Bearer $CRON_SECRET` or HMAC `X-Email-Webhook-Signature`.
- Admin API: session + `isPlatformAdmin`.
- Inbound: 4-layer injection pipeline before any LLM call.
- Outbound: output validation on generated replies.

## Schema-only tables (001 — not wired)

<Callout type="development" title="Deprecated column-model tables — no app access">
`001_email_crm_schema.sql` defines **`email_analytics`**, **`email_knowledge_base`**, and **`email_security_events`**. No TypeScript module in the repo reads or writes these tables. Do not apply `001` on new deployments — use `009` + `010` JSONB migrations instead.
</Callout>

<Callout type="development" title="Backlog — persistence gaps">
| Table (001 schema) | Current implementation |
|--------------------|------------------------|
| `email_knowledge_base` | `getKnowledgeBaseService()` uses `InMemoryKnowledgeRepository` — PGVector table not connected |
| `email_security_events` | Security pipeline runs in-process; events are not persisted |
| `email_analytics` | Daily rollup table unused; admin analytics queries `email_api_usage` JSONB at runtime |
</Callout>
