# Backend modes and databases

<Callout type="info">
  Use the **Founder** / **Developer** tabs to filter this page for your role. The `DB_BACKEND_MODE` environment variable is **required** — the platform will not start without it.
</Callout>

Ring Platform uses a **single codebase** with a **required** runtime switch: **`DB_BACKEND_MODE`**. The value selects which database adapters are registered, whether Firestore is used for application data, and how push notifications are wired.

| Mode | Primary database | Firebase use | Best for |
|------|-----------------|--------------|----------|
| **`k8s-postgres-fcm`** | PostgreSQL 16 + PostGIS | FCM push only | Production self-hosted, local dev |
| **`firebase-full`** | Firestore **(first-class)** | Everything: DB, FCM, Storage, AI, Hosting | Vercel Edge, clones, rapid prototyping, no-PostgreSQL |
| **`supabase-fcm`** | Supabase PostgreSQL | FCM push only | Managed cloud PostgreSQL |

**Naming:** Production on your own Postgres is often described as "self‑hosted PostgreSQL + FCM" or "Postgres‑primary mode." The enum value remains `k8s-postgres-fcm` — renaming the string would break every deployment, secret store, and clone without a coordinated migration.

**Implementation files:** `lib/database/backend-mode-config.ts` (config), `lib/database/DatabaseService.ts` (service), `lib/database/BackendSelector.ts` (router), `lib/services/firebase-service-manager.ts` (SSOT helpers for `firebase-full`).

## Which mode should I choose?

| Scenario | Recommended mode | Why |
|----------|----------------|-----|
| Self-hosted production (k3s, K8s) | **k8s-postgres-fcm** | Full data sovereignty, PostgreSQL performance, PostGIS spatial queries |
| Rapid prototyping / MVP | **firebase-full** | Zero database provisioning, free FCM push, auto-scale, Firebase Hosting deploy |
| Ring clone (white-label) | **firebase-full** | No PostgreSQL dependency for the clone operator — clone is fully self-contained |
| Vercel Edge deployment | **firebase-full** | Vercel Edge Runtime + Firestore = no cold-start DB connection |
| Cloud PostgreSQL (no K8s) | **supabase-fcm** | Managed PostgreSQL with Supabase, FCM push |
| Push notifications needed | Any mode | FCM is optional and available in all three modes |

### firebase-full: first-class ring-db mode

**firebase-full** was elevated from prototyping to **first-class** production mode on 2026-06-30. It now includes:

- **30+ React 19 `cache()`-native SSOT helpers** for credit balance, subscriptions, payment transactions, wallet transactions, desk orders, and order history — all in `lib/services/firebase-service-manager.ts`
- **3 atomic write primitives** — single Firestore transaction for credit balance adjust, subscription status update, and payment transaction status append (ACID, no race conditions)
- **Firebase 14 Enterprise features** — pipeline operations, change streams, text search, geospatial search
- **FCM Admin HTTP v1 bridge** — push notifications with automatic invalid-token cleanup
- **AI Logic (Gemini 2.5/3.x)** — server-side text generation and chat
- **Firebase Hosting** — `firebase deploy --only hosting` deploys your Ring clone with canonical rewrite rules

### Cost comparison

| Aspect | k8s-postgres-fcm | firebase-full | supabase-fcm |
|--------|-----------------|---------------|--------------|
| Database | Infrastructure cost only | Pay-per-read/write | Supabase tier pricing |
| Push (FCM) | Free | Free | Free |
| Storage | Vercel Blob / self-hosted | Firebase Storage (free tier) | Supabase Storage |
| Compute | K8s / Docker | Vercel Edge / Cloud Run | Vercel / Cloud Run |
| AI | LLM client via `lib/ai/llm-client.ts` | Firebase AI Logic + Gemini 2.5/3.x | LLM client via `lib/ai/llm-client.ts` |

### Backend selection in code

```typescript
// lib/database/backend-mode-config.ts
export type BackendMode = 'k8s-postgres-fcm' | 'firebase-full' | 'supabase-fcm'

export function detectBackendMode(): BackendMode {
  const mode = process.env.DB_BACKEND_MODE as BackendMode | undefined
  if (!mode) throw new Error('DB_BACKEND_MODE is required')
  return mode
}

export function shouldUseFirebaseForDatabase(): boolean {
  return detectBackendMode() === 'firebase-full'
}
```

### Firebase in k8s-postgres-fcm and supabase-fcm

- **Application data** (collections routed through `DatabaseService` / `BackendSelector`) goes to **PostgreSQL** via `PostgreSQLAdapter`
- **`lib/firebase-admin.server.ts`** explicitly avoids real Firestore when `shouldUseFirebaseForDatabase()` is false — `getAdminDb()` returns a **mock** Firestore that never connects
- **FCM** still uses Firebase project credentials where enabled. That is **push delivery only**, not the primary transactional store
- **`build-mock.server.ts`** now provides **7 mock classes** (`MockFirestore`, `MockAuth`, `MockDatabase`, `MockMessaging`, `MockStorage`, `MockAppCheck`, `MockRemoteConfig`) — all returned as type-compatible mocks during SSG and k8s-postgres-fcm mode

### Firebase in firebase-full mode

- **ALL application data** (every collection routed through `DatabaseService`) goes to **Firestore** via `FirebaseAdapter`
- **`lib/services/firebase-service-manager.ts`** provides **30+ React 19 `cache()`-native SSOT helpers** for the canonical collection shapes: `users/{userId}.credit_balance` (fiat USD), `users/{userId}.credit_transactions[]` (array), `subscription_ledger` (single source of truth), `payment_transactions` (PaymentConductor), `wallet_transactions` (chain activity), `desk_orders` (credit↔token conversion), `orders` (membership + store)
- **3 atomic write primitives** (`creditBalanceAdjustAtomic`, `subscriptionStatusUpdateAtomic`, `paymentTransactionAppendStatusAtomic`) wrap read-modify-write in a single Firestore transaction — prevents the race that affected the legacy `addCredits`/`spendCredits` pattern
- **6 real-time listener factories** (`createCreditBalanceListener`, `createSubscriptionListener`, `createPaymentTransactionListener`, `createWalletTransactionListener`, `createDeskOrderListener`, `createOrderListener`) pair with Tunnel for live UI updates without polling
- **Firebase 14 Enterprise** features available via `FirebaseAdapter`: pipeline operations (`runPipeline`), change streams (`onCollectionChange`), text search (`textSearch`), geospatial (`geoSearch`)

### React 19 cache() pattern

Every SSOT read helper in `firebase-service-manager.ts` is wrapped in React 19 `cache()`:

```typescript
import { cache } from 'react'

export const getCachedUserCreditBalance = cache(async (userId: string) => {
  // Firestore read — cached for the duration of the request
})

export const getCachedActiveSubscription = cache(async (userId: string) => {
  // Query subscription_ledger — deduplicated if called twice
})
```

This eliminates duplicate Firestore reads within a single SSG/SSR cycle — typical 3–7× reduction in read operations.

### Supabase: two different roles

1. **`DB_BACKEND_MODE=supabase-fcm`** — PostgreSQL runs on Supabase; same "Postgres primary + FCM" pattern as k8s mode
2. **Tunnel realtime (`NEXT_PUBLIC_TUNNEL_TRANSPORT=supabase`)** — optional **Realtime** channel in `lib/tunnel/transports/supabase-transport.ts`, using `@supabase/supabase-js` and `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_ANON_KEY`. This is **orthogonal** to which SQL backend owns your tables — do not assume "Supabase in env" always equals `supabase-fcm` mode

### Auth.js and database mode

Auth tables (`users`, `accounts`, `sessions`, `verification_tokens`, …) are part of the **PostgreSQL** schema when using the PostgreSQL adapter (k8s-postgres-fcm, supabase-fcm) or live in **Firestore** when using the Firebase adapter (firebase-full). See `lib/auth/postgres-adapter.ts` / `data/schema.sql` for the SQL path, and `lib/auth/firebase-adapter.ts` for the Firestore path.

### React 19 + React 16 compatibility

All SSOT helpers and adapter methods are `async` (Promise-based) so they are compatible with:
- React 19 `use()` for Suspense-based data fetching
- `useActionState` for Server Action forms
- Regular `await` in Server Components and Route Handlers
