# Best Practices

Development patterns and conventions specific to Ring Platform.

<Audience for="founder">

## Development Principles

### Quality over quantity
Ring Platform is a multi-tenant white-label platform powering 15+ production clones. Every pattern must work identically across PostgreSQL-primary (`k8s-postgres-fcm`) and Firebase-backed deployments. The `DatabaseService` abstraction layer ensures this — write to `db()` once, run anywhere.

### Security by convention
- `userId` is **always** derived from `await auth()` in server code, never from client-supplied parameters.
- Payment operations run server-side only. WayForPay HMAC signatures verify callback authenticity.
- File uploads go through `file()` abstraction (`@/lib/file`) — access controls are enforced at the upload layer, never assumed from the client.

### i18n is not optional
All user-facing strings live in `locales/{locale}/` JSON bundles loaded by `next-intl`. Inline strings in components are a code smell. See `docs/en/architecture/proxy-and-intl.mdx` for the i18n architecture.

### Respect the backend mode
`DB_BACKEND_MODE` selects the database adapter at runtime. Do not import `firebase-admin` or `postgres` directly in domain code. Use `db()` from `@/lib/database` exclusively. See [Backend modes and databases](/en/docs/architecture/backend-modes-and-databases).

</Audience>

<Audience for="developer">

## Database Access

### The `db()` singleton

The primary database interface is the `db()` singleton from `@/lib/database`. It auto-initializes and provides typed `*Doc` methods that return `{ success, data, error }` result objects.

```typescript
import { db } from '@/lib/database'

// Create
const result = await db().createDoc('entities', { name: 'Acme', type: 'technology' })
if (!result.success) throw result.error

// Read by ID
const entity = await db().findDocById<Entity>('entities', id)
if (!entity.success) throw entity.error

// Query with filters
const results = await db().queryDocs<Entity>({
  collection: 'entities',
  filters: [{ field: 'status', operator: '==', value: 'active' }],
  orderBy: [{ field: 'name', direction: 'asc' }],
  pagination: { limit: 20, offset: 0 },
})

// Update
await db().updateDoc('entities', id, { name: 'Acme Corp' })

// Delete
await db().deleteDoc('entities', id)
```

<Callout type="info">
The `db()` singleton survives Next.js dev HMR via `globalThis.__ringDatabaseService`. The database initializes once and reuses the connection across hot reloads.
</Callout>

### Transactions

Use `db().transaction()` for atomic multi-step writes. The transaction callback receives an `IDatabaseTransaction` with `create`, `read`, `update`, `delete` methods. Errors **throw** — do not check `result.success` inside a transaction.

```typescript
import { db } from '@/lib/database'

await db().transaction(async (txn) => {
  const existing = await txn.read('usernames', usernameKey)
  if (existing) throw new Error('Username is taken')

  await txn.create('usernames', { userId, reservedAt: new Date() }, { id: usernameKey })
  await txn.update('users', userId, { username })
})
```

### Direct service access (advanced)

For custom backend routing or multi-adapter operations, import the `DatabaseService` class directly:

```typescript
import { getDatabaseService } from '@/lib/database/DatabaseService'
const svc = getDatabaseService()
await svc.initialize()
```

See [Backend modes and databases](/en/docs/architecture/backend-modes-and-databases) for details on adapter selection and sync.

<Callout type="warning">
Do **not** use raw Firestore or pg queries in feature code. Every database operation must go through `DatabaseService` so the platform can switch backends without rewriting business logic.
</Callout>

## Server Actions

All Server Actions live in `app/_actions/` and follow a consistent pattern.

### Conventions

1. File-level `'use server'` directive at the top.
2. `import { auth } from '@/auth'` for session — never accept `userId` from the client.
3. Return form-state objects `{ success?: boolean, error?: string, message?: string }`.
4. Use `localizedRedirect` for navigation after success.
5. Zod or manual validation at the boundary.

```typescript
'use server'

import { auth } from '@/auth'
import { db } from '@/lib/database'
import { revalidatePath } from 'next/cache'
import { localizedRedirect } from '@/lib/i18n-server-redirect'
import type { Locale } from '@/i18n/shared'

export interface ActionResult {
  success?: boolean
  error?: string
  message?: string
  fieldErrors?: Record<string, string>
}

export async function createEntity(
  prevState: ActionResult | null,
  formData: FormData,
  locale: Locale
): Promise<ActionResult> {
  const session = await auth()
  if (!session?.user?.id) return { error: 'Authentication required' }

  // Validate
  const name = formData.get('name') as string
  if (!name?.trim()) return { error: 'Name is required' }

  // Write
  const result = await db().createDoc('entities', {
    name: name.trim(),
    createdBy: session.user.id,
    createdAt: new Date(),
  })

  if (!result.success) return { error: result.error?.message ?? 'Creation failed' }

  revalidatePath(`/${locale}/entities`)
  localizedRedirect({ locale, href: '/entities' })
}
```

### Error handling

- Return error strings for form display. Do not throw in form-returning actions.
- Throw only for non-recoverable errors (misconfiguration, missing env vars).
- Wrap `localizedRedirect` in try/catch — it throws `NEXT_REDIRECT` which must propagate.

<Callout type="tip">
Check `app/_actions/vendor-actions.ts` for a comprehensive real-world example covering file uploads (Vercel Blob via `file()`), nested create + update, and multi-step onboarding flows.
</Callout>

## Authentication

### Server-side (`@/auth`)

Import `auth` from the project root `@/auth` (not `next-auth` or `authjs` directly — Ring Platform provides a configured instance at `auth.ts`).

```typescript
import { auth } from '@/auth'

export async function getServerSession() {
  const session = await auth()
  return session
}
```

The `auth()` call is available in:
- Server Actions (`app/_actions/`)
- Route handlers (`app/api/`)
- Server Components (async component)
- Middleware

### Client-side (`useSession`)

```typescript
'use client'

import { useSession } from '@/auth/client'

export function UserInfo() {
  const { data: session, status } = useSession()

  if (status === 'loading') return <div>Loading...</div>
  if (!session?.user) return <div>Not signed in</div>

  return <div>{session.user.name}</div>
}
```

### Auth.js (NextAuth v5) configuration

The canonical auth config is at `auth.ts` in the project root. It configures:
- Credentials provider (email/password)
- Google OAuth provider
- JWT strategy (with refresh token rotation)
- PostgreSQL adapter (`lib/auth/postgres-adapter.ts`)

Do not create additional `auth.ts` files in features. Extend the root config.

<Callout type="warning">
Never pass `userId` from the client to a Server Action or API route. Derive it from `await auth()` server-side. See `app/_actions/fcm.ts` for the canonical pattern — `userId is derived from auth() only — never pass userId from the client`.
</Callout>

## Push Notifications (FCM)

FCM token registration and unregistration flow through Server Actions in `app/_actions/fcm.ts`. The underlying DB operations live in `lib/notifications/fcm-token-db.ts`.

```typescript
'use server'

import { auth } from '@/auth'
import { upsertFcmTokenForUser, unregisterFcmTokenForUser } from '@/lib/notifications/fcm-token-db'
import type { UpsertFcmTokenParams, UpsertFcmTokenResult } from '@/lib/notifications/fcm-token-db'

export async function upsertFcmToken(params: UpsertFcmTokenParams): Promise<UpsertFcmTokenResult> {
  const session = await auth()
  if (!session?.user?.id) return { error: 'Authentication required' }
  return upsertFcmTokenForUser(session.user.id, params)
}
```

Send notifications server-side using `ring-mcp_ring-fcm-send` tool or direct Firebase Admin messaging. Never expose FCM server keys to the client.

## Payments (WayForPay)

Ring Platform uses WayForPay as the primary payment provider. Key patterns:

- **All payment logic is server-side only** — never expose API keys or HMAC secrets to the client.
- **Idempotent `orderReference`** — every payment attempt has a unique `orderReference` to prevent duplicate charges.
- **HMAC verification** — webhook callbacks are verified using HMAC MD5 before processing.
- **3DS handling** — WayForPay redirects are managed through `components/store/checkout/`.

See `docs/en/architecture/payment-conductor.mdx` for the full payment architecture, webhook flow, and refund patterns.

## Server vs Client Component Boundaries

- **Default to Server Components** — fetch data and render on the server.
- **Push client boundaries down** — wrap interactive elements (forms, maps, real-time) in `'use client'` leaves.
- **Avoid useEffect for data fetching** — use Server Actions, Route Handlers, or `useActionState` in React 19.

```typescript
// page.tsx — Server Component (default)
export default async function EntitiesPage({ params: { locale } }: Props) {
  const session = await auth()

  const result = await db().queryDocs<Entity>({
    collection: 'entities',
    filters: [],
    pagination: { limit: 20 },
  })

  return <EntityList entities={result.data ?? []} session={session} />
}
```

## File Uploads

Use the `file()` abstraction from `@/lib/file` rather than directly calling Vercel Blob or S3 APIs.

```typescript
import { file } from '@/lib/file'

const result = await file().upload(`entities/${entityId}/logo.webp', fileObject, {
  access: 'public',
  addRandomSuffix: false,
})
if (!result.success) throw new Error(result.error)
```

## Testing Patterns

Tests live in `__tests__/` and use Jest (with `@jest-environment jsdom` for component tests) or Vitest.

### Mock external services, not DatabaseService

Ring Platform tests mock at the boundary — constants, `next/link`, translation bundles — but do **not** mock `@/lib/database` with fake Firestore. Database-dependent logic is tested either against a real test database or through integration tests that exercise the full adapter stack.

<Callout type="tip">
See [Testing Guide](/en/docs/development/testing) for the full testing strategy, and examine real test files in `__tests__/features/` (e.g. `news-visibility-filter.test.ts`, `referral-commission.test.ts`) for patterns that test pure business logic without database mocking.
</Callout>

### Component testing example

```typescript
/**
 * @jest-environment jsdom
 */

import { render, screen } from '@testing-library/react'
import { NextIntlClientProvider } from 'next-intl'
import EntityCard from '@/components/EntityCard'
import type { Locale } from '@/i18n/shared'

// Mock next/link
jest.mock('next/link', () => {
  return ({ children, href }: { children: React.ReactNode; href: string }) => (
    <a href={href}>{children}</a>
  )
})

const mockMessages = {
  'entities.card.viewDetails': 'View Details',
}

describe('EntityCard', () => {
  it('renders entity name', () => {
    const entity = { id: '1', name: 'Test Entity', type: 'technology' }

    render(
      <NextIntlClientProvider locale="en" messages={mockMessages}>
        <EntityCard entity={entity} />
      </NextIntlClientProvider>
    )

    expect(screen.getByText('Test Entity')).toBeInTheDocument()
  })
})
```

## Performance

### Database query patterns

- Use `db().queryDocs()` with `filters` and `pagination` to limit results at the database level — do not fetch all documents and filter in application code.
- Use `db().findDocById()` for single-document lookups instead of `queryDocs({ filters: [{ field: 'id', operator: '==', value: id }] })`.
- The entity cache in `DatabaseService` provides 30-second TTL for read-after-write consistency on `entities` collection — no manual caching needed for basic cases.

### React performance

- Server Components by default — zero client JS for pure rendering.
- `useActionState` (React 19) for form state management in client components — no external state library needed.
- Dynamic imports with `next/dynamic` for heavy client components (maps, editors, charts).

## Code Organization

- **`app/_actions/`** — all Server Actions, one file per domain.
- **`features/{domain}/services/`** — business logic that can be called from Server Actions or Route Handlers.
- **`features/{domain}/lib/`** — domain-specific pure functions and utilities.
- **`lib/database/`** — database abstraction. Do not add feature-specific database queries here.
- **`components/`** — shared UI components only. Feature-specific components live in `features/{domain}/components/`.

See [Code Structure](/en/docs/development/code-structure) for the full directory layout.
