# Performance Optimization

Profiling and optimization strategies specific to Ring Platform. This document covers real codebase patterns. For user-facing performance expectations, see [Performance](/docs/en/features/performance). For production hardening, see [Deployment Performance](/docs/en/deployment/performance). For general development conventions, see [Best Practices](/docs/en/development/best-practices).

<Callout type="warning">
  Ring Platform does **not** use client-side Firestore. Firebase is Admin SDK only via `lib/firebase-admin.server.ts`. The only client-side Firebase code is `public/firebase-messaging-sw.js` for FCM push notifications.
</Callout>

<Audience for="founder">

## What Affects Load Times

Ring Platform loads fast because most pages are **React Server Components** rendered on the server. Key factors that influence performance:

- **Server data caching** — repeated Firestore reads during a single request are deduplicated with React 19 `cache()`.
- **Build-time optimizations** — Firebase Admin is mocked during static generation, cutting build time by ~31%.
- **Minimal client JavaScript** — only pages with interactivity (forms, maps, checkout) use client components.
- **CDN-served assets** — static pages are pre-built and served from edge cache.

## Performance Optimizations Available

| Optimization | Benefit |
|---|---|
| React 19 cache() | Deduplicates Firestore reads per request |
| Build-time Firebase mocking | ~31% faster builds, prevents 22+ redundant initializations |
| DatabaseService query layer | Unified PostgreSQL + Firestore with caching |
| Server Components by default | No client JS for most pages |
| WayForPay server-side only | No payment logic exposed to the client |
| FCM service worker | Push notifications handled off main thread |

## React 19 cache() for Data Deduplication

The `firebase-service-manager.ts` module wraps every Firestore Admin SDK read with React 19 `cache()`. This prevents duplicate requests within the same Server Component render pass.

```typescript
import { getCachedDocument, getCachedCollection } from '@/lib/services/firebase-service-manager'

// Multiple calls to the same document during SSG resolve to one Firestore read
const entity = await getCachedDocument('entities', 'abc123')
const sameEntity = await getCachedDocument('entities', 'abc123') // cache hit

// Collection queries also cached per-request
const activeEntities = await getCachedCollection('entities', {
  where: { field: 'status', operator: '==', value: 'active' },
  orderBy: { field: 'createdAt', direction: 'desc' },
  limit: 20
})
```

The `cache()` function is imported from React 19 — it is not a custom implementation. All cached read functions are in `lib/services/firebase-service-manager.ts` and work with `firebase-admin/firestore`.

<Callout type="tip">
  Cache scope is the current Server Component render pass only. After the response is sent, the cache is discarded. For longer-lived caching, use `revalidate` on fetch or a dedicated cache layer.
</Callout>

## Build-time Firebase Mocking

During `next build`, `NEXT_PHASE=phase-production-build` is set. The module at `lib/firebase/build-mock.server.ts` detects this and returns mock Firestore, Auth, and RTDB instances. This prevents ~22 Firebase Admin initializations that would otherwise run during static generation.

```typescript
import { isBuildTime, getMockFirebaseServices } from '@/lib/firebase/build-mock.server'

if (isBuildTime()) {
  const { mockDb, mockAuth } = getMockFirebaseServices()
  // mockDb.collection('test').get() returns empty results
  // No Firebase credentials needed during build
}
```

The mock layer implements the full Firestore query interface with chainable `where()`, `orderBy()`, `limit()`, and pagination methods — all returning empty result sets. Auth methods return safe default user objects. This is active at `lib/firebase/build-mock.server.ts:36`.

## DatabaseService Query Optimization

The database abstraction layer at `lib/database/DatabaseService.ts` provides a unified query API over PostgreSQL and Firestore, with built-in 30-second entity caching.

```typescript
import { getDatabaseService } from '@/lib/database/DatabaseService'

const db = getDatabaseService()
const result = await db.query({
  collection: 'entities',
  filters: { status: 'active' },
  orderBy: { field: 'createdAt', direction: 'desc' },
  pagination: { limit: 20 }
})

if (!result.success) {
  throw result.error || new Error('Query failed')
}
```

The service includes an `EntityCache` class with TTL-based invalidation. For read-after-write consistency, write operations invalidate the affected keys.

<Callout type="warning">
  Do not call `db.users.findById()` or similar patterns. The DatabaseService API uses `db.query({ collection, filters })` with a single options object. See `lib/database/DatabaseService.ts:74` for the full interface.
</Callout>

## Server Components by Default

All pages in `app/` are Server Components unless they carry a `'use client'` directive. This eliminates client-side JavaScript for most routes. Client components are used only for:

- Interactive forms (checkout, vendor onboarding)
- Map views (Ringdom Maps)
- Wallet and payment UIs
- Admin dashboards

Search `'use client'` in `app/` to see the full inventory of client components.

## FCM Background Message Handling

Firebase Cloud Messaging is handled entirely in the service worker at `public/firebase-messaging-sw.js`. Push events are processed without waking the main JavaScript thread. The client only registers the service worker and forwards the FCM token to the server.

## WayForPay Server-Side Only

Payment requests are server-side only. No WayForPay merchant credentials, HMAC keys, or payment logic are exposed to the browser. The client submits an order reference; the server constructs and verifies all payment payloads. See [WayForPay Integration](/docs/en/features/wayforpay-integration).

## Next.js 16 Rendering Strategies

Use `force-dynamic`, `force-static`, or `revalidate` exports per page to control rendering:

```typescript
// Static page, revalidated every 60 seconds
export const revalidate = 60

// Fully dynamic — no caching
export const dynamic = 'force-dynamic'
```

Static generation is the default. Explicitly mark pages as `force-dynamic` when they display user-specific data.

## Monitoring

Web Vitals are collected in production. Configure analytics tracking in the deployment environment. For build-time analysis, run:

```bash
npm run build
npm run analyze
```

The `firebase-service-manager.ts` module also exposes internal cache metrics:

```typescript
import { getCacheMetrics } from '@/lib/services/firebase-service-manager'

const metrics = getCacheMetrics()
console.log(`Hit rate: ${metrics.hitRate.toFixed(1)}%`)
```
