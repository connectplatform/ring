# k8s-postgres-fcm Mode

<Callout type="success">
  **k8s-postgres-fcm** is the recommended backend mode for production and local development. PostgreSQL on Kubernetes (or your local host) handles all application data, while Firebase Admin SDK is initialized exclusively for FCM push messaging and Apple Push. No Firebase vendor lock for application data.
</Callout>

<Audience for="founder">

## What k8s-postgres-fcm gives you

- **Full ownership of application data** — stored in PostgreSQL 16 on your infrastructure. No Firestore reads or writes.
- **Zero Firebase vendor lock for data** — migration or provider change touches only the database connection string, not application code.
- **Optional push notifications** — FCM and Apple Push remain available without exposing your database to Firebase.
- **Auth.js v5 integration** — authentication tables (users, accounts, sessions) live in PostgreSQL alongside business data.
- **PostGIS support** — enable spatial queries for store delivery radius, entity locations, event venues, and real estate features.
- **Native WebSocket transport** — tunnel uses native WSS via `TUNNEL_HUB_MODE=k8s-postgres` (or in-memory hub for local development).

## When to choose this mode

| Scenario | Recommended mode |
|----------|-----------------|
| Self-hosted production on k3s | **k8s-postgres-fcm** |
| Local development with PostgreSQL | **k8s-postgres-fcm** |
| Cloud PostgreSQL (no K8s) | supabase-fcm |
| Rapid prototyping / Vercel Edge | firebase-full |
| Push notifications needed | any mode — FCM is optional in all three |

## Cost profile

- **PostgreSQL** — runs on your own infrastructure (Kubernetes StatefulSet, bare metal, or Docker). No per-query cost.
- **Firebase FCM** — push notifications are free at any scale. Firebase project credentials are required only if you enable push.
- **No Firestore costs** — Firestore is never used for application data in this mode. The `getAdminDb()` call returns a mock Firestore instance that never connects.

</Audience>

## Architecture

```
┌─────────────────────────────────────────────────┐
│                Next.js 16 App                     │
│                                                   │
│  ┌──────────────────────┐  ┌──────────────────┐  │
│  │  PostgreSQLAdapter   │  │  Firebase Admin   │  │
│  │  (all CRUD / query)  │  │  (FCM + Apple     │  │
│  │                      │  │   Push only)      │  │
│  │  • Auth.js tables    │  │                   │  │
│  │  • Entities          │  │  • getAdminDb()   │  │
│  │  • Store products    │  │    → mock (never  │  │
│  │  • Conversations     │  │      connects)    │  │
│  │  • FCM tokens        │  │  • getAdminAuth() │  │
│  │  • All business data │  │    → mock         │  │
│  └────────┬─────────────┘  └────────┬─────────┘  │
│           │                         │            │
└───────────┼─────────────────────────┼────────────┘
            │                         │
            ▼                         ▼
   ┌─────────────────┐     ┌──────────────────┐
   │  PostgreSQL 16   │     │  Firebase FCM    │
   │  + PostGIS       │     │  (push only)     │
   │  StatefulSet     │     └──────────────────┘
   │  (k8s or local)  │
   └─────────────────┘
```

**Key decision points in code:**

- `shouldUseFirebaseForDatabase()` returns `false` — `getAdminDb()` returns a mock `Firestore` from `build-mock.server.ts` that never connects to Firebase.
- `shouldInitializeFirebaseFCM()` returns `true` — Firebase Admin SDK is initialized for push messaging only.
- `shouldInitializeApplePush()` returns `true` — Apple Push Notification Service is available.
- The `PostgreSQLAdapter` implements `IDatabaseService` and handles all CRUD, query, transaction, and count operations.

## Required environment variables

```bash
# Mode selection (REQUIRED — platform will not start without it)
DB_BACKEND_MODE=k8s-postgres-fcm

# PostgreSQL connection
DB_HOST=localhost               # K8s: postgres.<namespace>.svc.cluster.local
DB_PORT=5432
DB_NAME=ring_platform
DB_USER=ring_user
DB_PASSWORD=ring_password_2024

# Connection pool tuning (optional, shown with defaults)
DB_POOL_SIZE=20                 # Max connections in pool
DB_TIMEOUT=30000                # Connection timeout in ms
DB_RETRIES=3                    # Retry attempts on failure
DB_SSL=false                    # Set to true for production and Supabase

# PostGIS (optional)
DB_ENABLE_POSTGIS=false         # Enable spatial extensions
```

| Variable | Required | Default | Description |
|----------|----------|---------|-------------|
| `DB_BACKEND_MODE` | Yes | — | Must be `k8s-postgres-fcm` |
| `DB_HOST` | Yes | `localhost` | PostgreSQL hostname |
| `DB_PORT` | No | `5432` | PostgreSQL port |
| `DB_NAME` | Yes | `ring_platform` | Database name |
| `DB_USER` | Yes | `ring_user` | Database user |
| `DB_PASSWORD` | Yes | `ring_dev_password` | Database password |
| `DB_POOL_SIZE` | No | `20` | Connection pool max size |
| `DB_TIMEOUT` | No | `30000` | Connection timeout (ms) |
| `DB_RETRIES` | No | `3` | Connection retry count |
| `DB_SSL` | No | `false` | Enable TLS for PostgreSQL |
| `DB_ENABLE_POSTGIS` | No | `false` | Enable PostGIS extensions |

Only required if you need push notifications. Without these, the platform runs on PostgreSQL alone.

## PostgreSQL connection configuration

The `PostgreSQLAdapter` builds the pool config from env vars. Source: `lib/database/adapters/PostgreSQLAdapter.ts`:

```typescript
const poolConfig = {
  host: config.connection.host || 'localhost',
  port: config.connection.port || 5432,
  database: config.connection.database || 'ring_platform',
  user: config.connection.username || 'ring_user',
  password: config.connection.password || 'ring_dev_password',
  max: config.options.poolSize || 20,
  idleTimeoutMillis: config.options.timeout || 30000,
  connectionTimeoutMillis: config.options.timeout || 2000,
}
```

The adapter uses a **JSONB hybrid schema**: most tables store business data in a `data` JSONB column alongside top-level `id`, `created_at`, `updated_at` columns. Tables with fully normalized schemas (e.g., `vendor_applications`, `vendor_profiles`) list all columns in the `fieldMappings` map so the query builder uses direct column references instead of `data->>'field'`.

The adapter supports the full `DatabaseService` contract:

```typescript
// Single document operations
await db.findById('users', userId)
await db.create('users', { name: 'Alice', email: 'alice@example.com' })
await db.update('users', userId, { name: 'Bob' })
await db.delete('users', userId)

// Queries with filters, ordering, pagination
await db.query({
  collection: 'entities',
  filters: [{ field: 'status', operator: 'eq', value: 'active' }],
  orderBy: [{ field: 'createdAt', direction: 'desc' }],
  pagination: { limit: 20, offset: 0 },
})

// Transactions
await db.transaction(async (txn) => {
  const order = await txn.create('orders', { total: 100 })
  await txn.update('stock', productId, { quantity: 5 })
})
```

## Local setup

1. **Start PostgreSQL** (two options):

   ```bash
   # Option A: Docker (recommended)
   docker run -d --name ring-postgres-dev \
     -e POSTGRES_USER=ring_user \
     -e POSTGRES_PASSWORD=ring_password_2024 \
     -e POSTGRES_DB=ring_platform \
     -p 5432:5432 \
     postgres:16-alpine

   # Option B: Homebrew (macOS)
   brew install postgresql@16
   brew services start postgresql@16
   createdb ring_platform
   ```

2. **Create `.env.local`** from the template and set:

   ```bash
   DB_BACKEND_MODE=k8s-postgres-fcm
   DB_HOST=localhost
   DB_PORT=5432
   DB_NAME=ring_platform
   DB_USER=ring_user
   DB_PASSWORD=ring_password_2024
   ```

3. **Apply the schema**:

   ```bash
   psql -h localhost -U ring_user -d ring_platform -f data/schema.sql
   ```

4. **Start the dev server**:

   ```bash
   npm run dev
   ```

   The platform validates `DB_BACKEND_MODE` at startup and logs the backend configuration. You should see `Database: PostgreSQL` in the startup log.

**Tunnel hub for real-time features:**

In local development, the tunnel defaults to an in-memory hub. For production-like behaviour, set:

```bash
TUNNEL_HUB_MODE=k8s-postgres
```

This stores tunnel state in PostgreSQL instead of process memory.

## K8s production setup

### 1. Namespace isolation

Each ring clone gets its own namespace: `k8s/namespace.yaml`

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: ring-platform-org
  labels:
    app.kubernetes.io/name: ring-platform-org
    app.kubernetes.io/part-of: ringdom
```

### 2. PostgreSQL StatefulSet

The `k8s/postgres.yaml` manifest deploys PostgreSQL 16 (image: `postgres:15`) as a single-replica Deployment with a `ClusterIP` service:

- **ConfigMap** (`postgres-config`) — POSTGRES_USER, POSTGRES_PASSWORD, POSTGRES_DB
- **Init SQL** — creates the application user (`platform_org_user`) and grants privileges
- **Extensions** — `uuid-ossp` and `btree_gin` enabled by default
- **Storage** — hostPath volume at `/data/postgres-<clone-name>`
- **Service** — resolves as `postgres.<namespace>.svc.cluster.local`

### 3. Secrets and ConfigMap

**Secrets** (`k8s/secrets.yaml` — Opaque, `stringData`):

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: ring-platform-org-secrets
type: Opaque
stringData:
  DB_PASSWORD: <value>
  AUTH_FIREBASE_PROJECT_ID: <value>
  AUTH_FIREBASE_CLIENT_EMAIL: <value>
  AUTH_FIREBASE_PRIVATE_KEY: |
    -----BEGIN PRIVATE KEY-----
    ...
    -----END PRIVATE KEY-----
```

**ConfigMap** (`k8s/secrets.yaml` — ConfigMap section):

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: ring-platform-org-config
data:
  DB_BACKEND_MODE: k8s-postgres-fcm
  DB_HOST: postgres.ring-platform-org.svc.cluster.local
  DB_PORT: "5432"
  DB_NAME: ring_platform
  DB_USER: ring_user
  DB_POOL_SIZE: "20"
  DB_TIMEOUT: "30000"
  DB_RETRIES: "3"
  DB_SSL: "false"
  NEXT_PUBLIC_FIREBASE_PROJECT_ID: <value>
```

**Important**: `DB_PASSWORD` goes in the Secret, not the ConfigMap. The deployment references it via `secretKeyRef`.

### 4. App deployment

`k8s/deployment.yaml` — Next.js 16 app with:

- Image: `ghcr.io/connectplatform/ring:v<version>-<clone>-amd64`
- 256Mi request / 1Gi limit memory
- 200m / 1000m CPU
- Liveness + readiness + startup probes (`/api/health`)
- Env vars from ConfigMap (non-sensitive) and Secret (sensitive)
- Persistent volume for file uploads (`pvc-local-file-storage.yaml` — 20Gi)
- Pod anti-affinity for HA

### 5. Ingress

`k8s/ingress.yaml` — nginx ingress controller with:

- Let's Encrypt TLS (cert-manager `letsencrypt-prod`)
- WebSocket support (proxy timeout 3600s, `websocket-services` annotation)
- Large proxy buffer (32k — Next.js emits large Link headers for hreflang)
- Rate limiting (100 RPS, 50 connections)
- 50MB body size limit

### 6. Apply the stack

```bash
kubectl apply -f k8s/namespace.yaml
kubectl apply -f k8s/postgres.yaml
kubectl apply -f k8s/secrets.yaml
kubectl apply -f k8s/deployment.yaml
kubectl apply -f k8s/service.yaml
kubectl apply -f k8s/ingress.yaml
kubectl apply -f k8s/pvc-local-file-storage.yaml
```

## Docker setup

For Docker-based local or production deployments, the `docker-compose.yml` supports `k8s-postgres-fcm` mode. Ensure your `.env` sets `DB_BACKEND_MODE=k8s-postgres-fcm` and the PostgreSQL connection variables:

```bash
docker compose up -d
```

Note: The default `docker-compose.yml` does not include a PostgreSQL service. You must either:
- Run PostgreSQL separately (native install or `docker run postgres:16-alpine`)
- Add a `postgres` service to your override (`docker/docker-compose.dev.yml`)

## FCM wiring notes

This mode uses Firebase Admin exclusively for push:

1. **Admin SDK initialization** — Firebase Admin app is created if `AUTH_FIREBASE_*` env vars are present. The SDK is needed for FCM token generation and push dispatch.
2. **Mock Firestore** — `getAdminDb()` returns a mock Firestore (never connects to Firebase). This is controlled by `shouldUseFirebaseForDatabase()` returning `false`.
3. **Mock Auth** — `getAdminAuth()` also returns a mock. Auth.js v5 handles all authentication.
4. **Client-side FCM** — The service worker (`public/firebase-messaging-sw.js`) runs in the browser and loads Firebase compat SDK from CDN. It is **not affected** by the backend mode — it always connects to Firebase for push subscription.
5. **FCM tokens** — Stored in the `fcm_tokens` PostgreSQL table via the `upsertFcmToken` Server Action.
6. **No Firebase env vars = no push** — If you omit all `AUTH_FIREBASE_*` and `NEXT_PUBLIC_FIREBASE_*` vars, Firebase Admin initialization is skipped entirely. PostgreSQL still works.

## Comparison: k8s-postgres-fcm vs supabase-fcm

| Aspect | k8s-postgres-fcm | supabase-fcm |
|--------|-----------------|--------------|
| **PostgreSQL host** | Your K8s or local | Supabase cloud |
| **SSL** | Optional (`DB_SSL=false` by default) | Required (`DB_SSL=true`) |
| **Connection pool** | `DB_POOL_SIZE=20` default | `DB_POOL_SIZE=10` default |
| **Auth credentials** | `DB_USER` / `DB_PASSWORD` | `SUPABASE_URL` / `SUPABASE_SERVICE_KEY` |
| **Deploy target** | K8s, Docker, bare metal | Supabase platform |
| **K8s manifests** | Full set in `k8s/` | Not applicable |
| **Tunnel hub** | `k8s-postgres` or `memory` | `memory` |
| **PostGIS** | `DB_ENABLE_POSTGIS=true` | Requires Supabase PostGIS addon |
| **Use case** | Full infra control | Managed cloud PostgreSQL |

Both modes use the same `PostgreSQLAdapter` class. The only difference is who hosts the PostgreSQL instance and how connection parameters are provided.
