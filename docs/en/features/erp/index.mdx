# Ring ERP

Ring ERP is the **operator cockpit** over the multi-vendor store: warehouse stock, checkout holds, paid-sale commit, and the vendor settlements ledger. It does **not** invent a second stock system — it extends `ERPStockService`, `inventory-sync`, and PaymentConductor paid handlers.

## What you get as an operator

| Surface | Route | Day-1 job |
|---------|-------|-----------|
| Store hub overview | `/admin/store` | Stock summary + pending settlements at a glance |
| Products / Orders | `/admin/store/products`, `/admin/store/orders` | Catalog approval and fulfillment status |
| Stock | `/admin/store/stock` | Low-stock filters, reason-coded restock, movement timeline |
| Commissions | `/admin/store/commissions` | Hold/release, dry-run due payouts, then process |
| Vendor stock | `/vendor/stock` | Own-product restock (bulk), low-stock badges |
| Vendor earnings | `/vendor/earnings` | Pending + history from `settlements` |

### Typical scenarios

1. **Prevent oversell** — Checkout reserves **sellable** units (`available`). A second checkout cannot take reserved stock.
2. **Paid order** — PaymentConductor marks paid → stock commits once (idempotent) → settlement row appears for each vendor slice.
3. **Buyer cancels unpaid** — Holds release; sellable returns. **Refund after paid** restores stock from sale movements (WayForPay Refunded/Voided wired).
4. **Payout day** — Dry-run due settlements, then Process due payouts (simulated badge until on-chain mode is verified).

<Callout type="tip">
  Default warehouse label is `zero-warehouse` (store id `1`). Nova Poshta pickup points in shipping APIs are **not** ERP warehouses.
</Callout>

### Shipped vs backlog

**Shipped (hub P0):** stock invariant, `commitSaleForOrder`, admin hub landing, stock/commissions depth, vendor ownership on restock.

## Architecture (verified)

<Mermaid title="Checkout reserve → paid commit → settlements">
{`sequenceDiagram
  participant CO as Checkout_Orders
  participant INV as inventory_sync
  participant PC as PaymentConductor
  participant SALE as commitSaleForOrder
  participant VS as VendorSettlementService
  participant DB as PostgreSQL

  CO->>INV: reserveInventoryForOrder
  INV->>DB: available-=q reserved+=q stock unchanged
  PC->>SALE: paid isNew
  SALE->>DB: fulfill reserved-=q then stock-=q
  PC->>VS: processSettlements
  VS->>DB: settlements ledger
`}
</Mermaid>

| Module | Path | Role |
|--------|------|------|
| Constants | `features/store/constants/stock.ts` | `ZERO_WAREHOUSE_ID`, `DEFAULT_INVENTORY_STORE_ID` |
| ERP stock | `features/store/services/erp-stock-service.ts` | Restock/adjust; levels-aware `getStockLevel` |
| Inventory sync | `features/store/services/inventory-sync.ts` | Reserve, fulfill, `commitSaleForOrder`, restore |
| Settlements | `features/store/services/settlement.ts` + `settlement-pipeline.ts` | Ledger + referral assists |
| Admin actions | `app/_actions/admin-store-erp.ts` | Init stock, hold/release, dry-run, adjust |
| Paid handlers | `lib/payments/conductor/handlers/store-order*.ts` + credit/token routes | Call `commitSaleForOrder` |

**Invariant:** `store_products.stock === inventory_levels.available + inventory_levels.reserved` · sellable = `available`.

ProcessConductor owns TTL cleanup (`cleanup-reservations`) and `settlement-payout` cron — do not duplicate.
