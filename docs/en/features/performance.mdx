# Performance Optimization Patterns

Ring Platform uses **React 19 `cache()`** for per-request data deduplication in Server Components, a **database abstraction layer** (`DatabaseService` + adapters) that routes to PostgreSQL or Firestore, and **Firebase Admin SDK** (`firebase-service-manager.ts`) for cached Firestore reads in `firebase-full` mode.

<Callout type="info">
  All code examples below reference **real files** in the codebase — `lib/services/firebase-service-manager.ts`, `lib/database/DatabaseService.ts`, `lib/database/adapters/FirebaseAdapter.ts`. Fabricated utilities (session-storage caches, custom RingApiClient, virtualizer patterns) are not part of Ring Platform.
</Callout>

## React 19 Server Components & Data Fetching

### Direct fetching in Server Components (preferred)

<Code language="typescript" title="Server Component data fetching">
{`// Services call DatabaseService (PostgreSQL or Firebase adapter)
import { getEntities } from '@/features/entities/services/entity-service'

export default async function EntitiesPage() {
  const entities = await getEntities()
  return <EntityGrid entities={entities} />
}`}
</Code>

Avoid calling your own HTTP API routes from Server Components — App Router Server Components can import services directly without a fetch round-trip.

### React 19 `cache()` for request deduplication

React 19's `cache()` deduplicates identical concurrent calls within the same request. Ring Platform uses this in two places:

**1. `firebase-service-manager.ts`** — cached Firestore reads (Admin SDK, `firebase-full` mode only):

<Code language="typescript" title="lib/services/firebase-service-manager.ts">
{`import { cache } from 'react'
import { getAdminDb } from '../firebase-admin.server'

export const getCachedDocument = cache(async (
  collection: string,
  docId: string
): Promise<DocumentSnapshot | null> => {
  const db = getAdminDb()
  const docRef = db.collection(collection).doc(docId)
  const doc = await docRef.get()
  return doc.exists ? doc : null
})`}
</Code>

**2. `DatabaseService`** — entity-level cache for read-after-write consistency (30-second TTL):

<Code language="typescript" title="lib/database/DatabaseService.ts (EntityCache)">
{`class EntityCache {
  private cache = new Map<string, { data: any; timestamp: number }>()
  private readonly TTL = 30000 // 30 seconds

  set(key: string, data: any) {
    this.cache.set(key, { data, timestamp: monotime() })
  }

  get(key: string) {
    const entry = this.cache.get(key)
    if (entry && (monotime() - entry.timestamp) < this.TTL) return entry.data
    this.cache.delete(key)
    return null
  }

  invalidate(key: string) { this.cache.delete(key) }
}`}
</Code>

## Database Abstraction Layer

### `DatabaseService` contract

The real `DatabaseService` (not the simplified illustration below) routes through `BackendSelector` to either `PostgreSQLAdapter` or `FirebaseAdapter`. Its query API uses a **single object parameter**:

<Code language="typescript" title="lib/database/DatabaseService.ts">
{`// Real API — single object parameter
const result = await db.query({
  collection: 'entities',
  filters: [{ field: 'status', operator: 'eq', value: 'active' }],
  orderBy: [{ field: 'createdAt', direction: 'desc' }],
  pagination: { limit: 20, offset: 0 }
})
// result: { success: boolean; data: DbRow<T>[]; error?: Error }

// Single document
const doc = await db.findById('users', userId)
// doc: { success: boolean; data: T | null; error?: Error }

// Mutations
await db.create('entities', data)
await db.update('entities', id, partial)
await db.delete('entities', id)

// Transactions
await db.transaction(async (txn) => {
  await txn.create('orders', orderData)
  await txn.update('inventory', productId, { stock: newStock })
})`}
</Code>

### FirebaseAdapter (Admin SDK — server-side only)

The **real** `FirebaseAdapter` uses `firebase-admin/firestore`, not the client Firebase SDK:

<Code language="typescript" title="lib/database/adapters/FirebaseAdapter.ts">
{`import { Firestore, FieldValue, Timestamp } from 'firebase-admin/firestore'
import { cert, getApps, initializeApp } from 'firebase-admin/app'

export class FirebaseAdapter implements IDatabaseService {
  private firestore: Firestore | null = null

  async findById<T>(collection: string, id: string): Promise<DatabaseResult<T>> {
    if (!this.firestore) await this.connect()
    const doc = await this.firestore.collection(collection).doc(id).get()
    if (!doc.exists) {
      return { success: true, data: undefined as any }
    }
    return { success: true, data: { id: doc.id, ...doc.data() } as T }
  }

  async query<T>(query: DatabaseQuery): Promise<DatabaseResult<T[]>> {
    // query = { collection, filters?, orderBy?, pagination? }
    // Uses admin SDK Query builder
    let q: FirebaseFirestore.Query = this.firestore.collection(query.collection)
    // ... filter, order, paginate, execute
    const snapshot = await q.get()
    return {
      success: true,
      data: snapshot.docs.map(doc => ({ id: doc.id, ...doc.data() })) as T[]
    }
  }
}`}
</Code>

**Key difference:** The doc example in earlier versions showed client-side `getFirestore()` from `firebase/firestore` — this is wrong for the platform's server-side adapter. The real adapter uses `firebase-admin/firestore` exclusively.

## Caching Strategy

| Layer | Scope | Mechanism | Location |
|-------|-------|-----------|----------|
| React `cache()` | Per-request | React 19 request dedup | `firebase-service-manager.ts` (Firebase) / Server Components |
| EntityCache | 30-second TTL | In-memory Map | `DatabaseService.ts` |
| HTTP/CDN | Page-level | Next.js `stale-while-revalidate` | `next.config.mjs` headers |

**No `sessionStorage` caching** is used on the server. Browser-side caching is left to standard Web API patterns (not part of this codebase).

## Firebase Optimization (FirebaseAdmin SDK)

### Batch operations

`firebase-service-manager.ts` provides:

<Code language="typescript" title="Real batch operations">
{`import { createBatchWriter, executeBatch } from '@/lib/services/firebase-service-manager'

const batch = createBatchWriter()
const ref1 = db.collection('entities').doc('id1')
batch.update(ref1, { status: 'archived' })
const ref2 = db.collection('entities').doc('id2')
batch.update(ref2, { status: 'archived' })
await executeBatch(batch)`}
</Code>

For Firestore's 500-item batch limit and compound index requirements, see [Firestore documentation](https://firebase.google.com/docs/firestore/query-data/indexing).

### Metrics tracking (debug only)

`firebase-service-manager.ts` includes optional development metrics (controlled by `FIREBASE_DEBUG_LOGS=true`):

<Code language="typescript">
{`// lib/services/firebase-service-manager.ts — debug metrics
const metrics = {
  cacheHits: 0,
  cacheMisses: 0,
  totalRequests: 0,
  getHitRate(): number {
    return this.totalRequests > 0 ? (this.cacheHits / this.totalRequests) * 100 : 0
  },
}

export function getCacheMetrics() {
  return {
    hitRate: metrics.getHitRate(),
    totalRequests: metrics.totalRequests,
    cacheHits: metrics.cacheHits,
    cacheMisses: metrics.cacheMisses
  }
}`}
</Code>

This is a dev/debug tool — **not a production monitoring system**. It logs to `console.log`, not to any external service. There is no performance budget enforcement in `next.config.mjs`.

## Summary

- **Real caching**: React 19 `cache()` for request dedup, EntityCache for 30-second read-after-write consistency
- **Real Firebase adapter**: `firebase-admin/firestore` (Admin SDK), never client-side `firebase/firestore`
- **Real `DatabaseService` contract**: `findById`, `query({collection, filters, orderBy, pagination})`, `transaction`
- **Fabricated patterns removed**: `SessionStorageCache`, `RingApiClient`, `DB_HYBRID_MODE` routing, `next.config performance budgets`, fake KPIs ("95% reduction", "17.0s", "55KB"), `trackWebVitals`, virtualizer
- **No performance benchmarks** are tracked in this codebase — profiling results belong in CI dashboards, not docs
