# Multi-Vendor Store

Ring Platform ships a multi-vendor marketplace where any **verified Entity** can operate a store, list products, and earn through automated commission settlements. The platform operator (Founder) earns from tiered commissions; vendors add products via a configurable product form with per-category custom fields and audience-gated visibility.

## Why the multi-vendor store matters for your clone

Every Entity in your Ring deployment can become a selling vendor — no external marketplace needed. The store generates platform revenue through **tier-based commission rates** (NEW → BASIC → VERIFIED → TRUSTED → PREMIUM, descending from 20% to 12%) on every sale. Vendors handle cataloguing themselves via the product form; operators review submissions through the admin product queue and process settlements in the commissions dashboard.

### Typical scenarios

- **A Ring clone for a local business network:** every shop in the city becomes a verified Entity and lists inventory in the store; transactions settle automatically.
- **A DAO marketplace:** member-gated products (courses, NFTs, service tiers) visible only to role-holders; public products serve as lead magnets.
- **A hosting/provider clone:** agencies and dev studios list managed Ring hosting packages; platform operator earns commission on every subscription.

### Product catalog SSOT

The full unfiltered product list is read once per cache window through `getCachedProductCatalog()` in `features/store/config.ts`:

<Code language="typescript" title="features/store/config.ts">{`export async function getCachedProductCatalog(): Promise<StoreProduct[]> {
  'use cache'
  cacheTag('store:products')
  cacheLife('minutes')

  const adapter = await getStoreAdapter()
  return adapter.listProducts()
}`}</Code>

| Consumer | Path | Role |
|----------|------|------|
| REST storefront API | `app/api/store/products/route.ts` (GET) | Filter/sort/paginate cached catalog |
| Server action | `app/_actions/store-products.ts` → `getStoreProducts()` | Same catalog + audience gating + price bounds |
| MCP tools | `app/api/mcp/v1/store/products/route.ts` (GET) | Direct adapter list for external agents |

**Cache invalidation:** after product create, call `updateTag('store:products')` — verified in `app/api/store/products/route.ts` (POST) and `app/api/mcp/v1/store/products/route.ts` (POST). New products appear immediately instead of waiting for `cacheLife('minutes')`.

### Deferred client fetch

`features/store/context.tsx` mounts `StoreProvider` globally (nav cart badge needs `totalItems` on every route) but **defers** the product-list network call:

- Loads only when `pathname` includes `/store` **or** the user already has cart items in `localStorage`.
- Uses module-scope single-flight (`fetchStoreProductsSingleFlight`) so concurrent mounts share one `GET /api/store/products`.
- Manual refresh via `refreshEnhancedProducts()` bypasses single-flight and hits the network fresh.

This follows the minimal-global-state pattern — no full catalog in client state until a store route or cart warrants it.

### Vendor store creation flow

When a vendor is approved, `createVendorProfile()` in `features/store/services/vendor-lifecycle.ts`:

1. Creates a `VendorProfile` with `store_activated: true` and `store_status: 'test'`
2. **Inherits store categories** from ring-config: `storeCategories: getSystemConfigSnapshot().store?.storeCategories ?? []`
3. Writes the profile to the `entities` collection (embedded) and `vendor_profiles` collection (mirror)
4. Publishes a `STORE_CREATED` event

Categories are defined in `ring-config.json` under `store.storeCategories` and shipped via SQL migration presets (`productFieldsPresets`).

### Product custom fields (per-category)

Vendors can add arbitrary name-value pairs to products, scoped by category. The flow:

<Steps>
  <Step>Vendor selects a category from the dropdown on the product form</Step>
  <Step>Clicks "Add product parameter" — a name+value input row appears</Step>
  <Step>Multiple parameters can be added and removed per product</Step>
  <Step>On save, custom fields are persisted to the `product_custom_fields` table via `createProductCustomField()` in `app/_actions/vendor-actions.ts`</Step>
</Steps>

**CRUD actions** (all auth-guarded via `getVendorEntity()` + product ownership verification):

<Code language="typescript" title="app/_actions/vendor-actions.ts">
{`await createProductCustomField({
  productId: 'product_123',
  category: 'organic-produce',
  fieldName: 'Soil Type',
  fieldValue: 'Loamy',
  fieldType: 'text',
})`}
</Code>

### Product audience filtering

Products carrying `productAudience: 'member'` are hidden from non-member visitors. Implemented in `app/_actions/store-products.ts` after catalog filters:

<Code language="typescript" title="app/_actions/store-products.ts">
{`const userHasMemberAccess = isAdmin || hasMemberPrivileges(currentRole)
if (!userHasMemberAccess) {
  filteredProducts = filteredProducts.filter(product => {
    const doc = product as unknown as Record<string, unknown>
    return doc.productAudience !== 'member'
  })
}`}
</Code>

The `hasMemberPrivileges()` guard checks `role >= member` (member, confidential, admin, superadmin).
